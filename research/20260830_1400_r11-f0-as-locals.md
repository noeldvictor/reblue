# 718,850 guest memory operations removed: r11 and f0 are locals now

2026-08-30. `non_argument_as_local` has been disabled in this repo for weeks with a
"DO NOT ENABLE. It miscompiles the guest." note. **96.7% of its value is now landed and working on
both desktop and a Quest 2**, because the flag was never one change.

## The flag was six changes wearing one name

Counted over `generated/reblue_recomp.*.cpp`:

| register | ctx accesses | share of the flag | functions that read it before writing it |
| --- | --- | --- | --- |
| **r11** | 632,902 | **85.1%** | **16** |
| **f0** | 85,929 | **11.6%** | **0** |
| r12 | 22,833 | 3.1% | **6,208** |
| r0 | 1,512 | 0.2% | 1 |
| r2 | 1 | ~0 | 0 |
| v32-v63 | 501 | 0.07% | 0 |

So the value and the risk sit in different registers. **r11 and f0 are 96.7% of the win with
essentially no hazard surface; r12 is 3% of the win and nearly all of the hazard** - and r12's
hazard has a named mechanism: with `skip_lr` the codegen emits `mflr r12` as a comment only, so the
next instruction reads a register nothing wrote.

## What landed

`scratch_r11_as_local` and `scratch_f0_as_local` in the SDK fork, plus `scratch_r12_as_local`,
`scratch_r0_r2_as_local` and `vector_v32_63_as_local` defined but off. The combined flag is kept
unchanged so existing manifests behave identically.

**Measured on the generated guest:**

```
ctx. accesses   2,049,805  ->  1,330,955     -35%
ctx.r11             632,902  ->  0
ctx.f0               85,929  ->  0
```

718,850 guest register memory operations removed, across all 18,777 functions. On ARM64 that matters
more than the count suggests: `ctx` is a reference that escapes into every `noinline` guest call, so
anything cached in a register must spill at every call and reload after it. A local can live in
x19-x28 across the call instead.

## Verified, both platforms

- **Desktop**, 175s autoplay run: no fatal lines, and the frame is unchanged - `far -4, near -26`
  crossed from `stereo_check --stacked`, identical to the baseline, with the same per-channel
  extrema and a correct-looking capture.
- **Quest 2**, 170s run: **no crash, and zero `file-load fatal` lines** - which is exactly the
  failure the combined flag produced ("dies 0.2s after the VFS mounts"). The frame time is unchanged
  because the device is currently GPU-bound (fence ~158ms of ~184ms), so this is a correctness
  result, not a speed one.

## Measured, on x86, by profile share

Frame time cannot settle this: a codegen flag is compile-time so `bd_ab_flag` cannot A/B it, and
cross-run `other_ms` drifts far more than the effect (the device readings either side of this change
were 23.55 and 23.90ms, well inside noise). **Profile share is run-normalised**, so it can.

Two 175-second desktop runs, same scene, flags the only difference:

| | samples | guest share | host share |
| --- | --- | --- | --- |
| **without** r11/f0 | 13,950 | **78.11%** | 21.89% |
| **with** r11/f0 | 14,511 | **76.74%** | 23.26% |

**-1.37 percentage points of guest CPU share**, about 1.8% relative. On ~14k samples the standard
error on a proportion is ~0.35pp, so this is ~4 sigma and a real signal rather than drift - though
two runs of autoplay are never quite the same scene, so treat it as "small and positive", not as a
precise figure.

**And note what platform that is.** The entire argument for this change is ARM64-specific: `ctx` is a
reference that escapes into every `noinline` guest call, so a `ctx.rN` the compiler had cached must
spill at each call and reload after it, where a local can sit in x19-x28 across the call. x86 has
fewer callee-saved registers to win with and much better store-to-load forwarding when it loses -
so a *small* win on x86 is exactly what the theory predicts, and the ARM64 win should be larger.

**It cannot be measured on ARM64 today**, because the device is GPU-bound and the guest is 0.1% of
device samples - the CPU is asleep on the fence. That measurement has to wait for the two-layer post
chain to come down, and the claim should stay "-1.37pp on x86, unmeasured on ARM64" until then.

## What is still off, and why

`scratch_r12_as_local` stays off: 3% of the value, 6,208 read-before-write candidates, and a known
mechanism for how it breaks. If someone wants it, the bisect set is those 6,208 functions and the
first thing to try is excluding the `mflr r12` sites. `scratch_r0_r2_as_local` and
`vector_v32_63_as_local` are worth ~0.3% combined and are not worth a build.

**If the guest ever regresses after this, turn these two off first** - they are independent switches
now, which is the whole point of the split.


## Next item checked and it is blocked, not easy: vectorising stvlx/stvrx

`build_stvlx` and `build_stvrx` (`out/rexglue-src/src/codegen/builders/memory.cpp:626-644`) emit a
loop of up to **16 individual byte stores** each, across 634 + 470 sites, and both carry a
`TODO(tomc): vectorize`. It looks like the obvious next win. It is not available:

```
#define REX_STORE_U8(x, y)  (*(volatile u8*)(base + (u32)(x) + ...) = (y))
```

**The stores are `volatile`, so no compiler may merge or vectorise them** - each is a mandated
separate access. Making the shuffle masks `const` (tried earlier today, measured byte-identical)
cannot help, because the obstacle is not the mask operand, it is the store.

So **B7 is not independent of the `volatile` question - it is downstream of it.** The only way to
vectorise these is to make the stores non-volatile for guest RAM, which is the store half of the
relaxation work.

That half is the *safer* half, and worth stating precisely: `volatile` exists here to stop the
compiler hoisting a **load** out of a guest spin-loop, which is what hangs the game when the global
relaxation is enabled. A relaxed **store** cannot hoist a poll out of a loop; the worst it can do is
merge or dead-store-eliminate. And the codegen already distinguishes MMIO, routing `eieio`-adjacent
accesses through `REX_MM_STORE_*`, so device memory is separable from RAM.

**Not attempted here.** The failure mode is silent memory corruption rather than a crash, the
verification (`bd_verify_guest_math`, which exercises `bdMatrixCopyAligned` - built entirely from
this idiom - and reports byte-exactness on the first frame) needs to be run first, and it should not
be landed in the same build as anything else.
