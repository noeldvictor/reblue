# Research: where the guest's CPU time goes, found by reading rather than profiling

Date: 2026-08-28 21:00
Topic: static analysis of the recompiled PowerPC hot path, with no device attached.

Gameplay runs at 4-8 fps on a Quest 2, and the frame breakdown says ~180ms of that is CPU against
~1ms on the GPU fence. The CPU is the recompiled PowerPC, so that is where a playable frame rate has
to come from. No headset was available, so this is what could be established by reading the
generated code and the SDK, and by compiling representative snippets for ARM64.

**Nothing here is a measured frame-rate improvement.** One change is measured, but the metric is
static (context accesses emitted by codegen), not fps. Both need a device before they can be called
wins. Recording the distinction because the opposite mistake has already been made twice in this
port.

---

## 1. The hot path is guest memory access

Every guest load and store in the entire game goes through one macro, in
`generated/reblue_pch.h`:

```c
#define REX_LOAD_U32(x) __builtin_bswap32(*(volatile u32*)(base + (u32)(x) + REX_PHYS_HOST_OFFSET(x)))
```

Two things to check, and one of them is a non-issue:

- **`REX_PHYS_HOST_OFFSET` is free on Android.** It is only non-zero on Win32 and Mac ARM64; on
  Android it expands to `0u` and disappears. Not a cost.
- **`volatile` is not free**, and it is on every access.

### What volatile actually costs, measured

Compiled a representative recompiled sequence - a guest stack spill, two reloads of it, and three
reads of the same struct field, which is exactly the shape recompiled PowerPC produces - for
`aarch64-linux-android29` at `-O2`, both ways:

| | instructions in the function |
| --- | --- |
| without `volatile` | **11** |
| with `volatile` | **23** |

The generated assembly says why. Without it, three reads of `r3+0x10` collapse into a single `ldr`
and the arithmetic folds to `add w8, w8, w8, lsl #1`. With it, all three `ldr` are emitted, each
with its own `rev`, and the spilled store cannot be forwarded to its reload.

This matters more here than it would in ordinary code. A 1:1 translation of PowerPC undoes the
original compiler's register allocation: every spill and reload the PPC compiler chose becomes a
real memory round trip, and `volatile` forbids the host compiler from undoing any of it.

### Why it cannot simply be deleted

`volatile` is presumably there to stop the compiler hoisting a load out of a guest spin-loop - a
guest thread polling a flag in shared memory would hang if its load were cached in a register. That
is a real hazard and a real bug class, so this needs an opt-in flag and on-device testing, not a
blanket removal. It is not attempted here.

## 2. Floating-point mode switching is already handled well

`disableFlushMode` appears 481 times in a single generated file, which looks alarming: PowerPC
FPSCR emulation, and writing ARM64's FPCR is serialising.

It is guarded:

```c
inline void disableFlushMode() noexcept {
  if ((csr & FlushMask) != 0) [[unlikely]] {   // usually just a test and branch
    csr &= ~FlushMask;
    setcsr(csr);
  }
}
```

So the common path is a compare against a cached copy, and the expensive `setcsr` only fires on an
actual change. **Not a bottleneck.** Recorded so nobody investigates it twice.

Indirect calls are fine too - `REX_CALL_INDIRECT_FUNC` is a range check and a table lookup with
`[[likely]]` on the hot path.

## 3. A codegen optimisation that was simply not switched on

The SDK exposes eight codegen flags. `reblue_manifest.toml` set six of them:

```toml
skip_lr = true
ctr_as_local = true
xer_as_local = true
cr_as_local = true
reserved_as_local = true
non_volatile_as_local = true
```

**`non_argument_as_local` was not set**, and it is the one that keeps the remaining scratch registers
in host registers rather than in the `PPCContext` struct. Enabling it:

| | `ctx.` accesses across generated/ | generated C++ |
| --- | --- | --- |
| before | 2,049,797 | 112.0 MB |
| after | **1,306,101** | 109.6 MB |

**743,696 fewer context accesses, a 36% reduction.** Each one was a load or store against the
context struct in memory; they are now candidates for living in an ARM64 register for the length of
a function.

Builds clean, 77 seconds for the full guest rebuild, and `libreblue.so` drops from 141 MB to 139 MB.

`skip_msr` is the eighth flag and is still off. Left alone for now: one change at a time, and MSR
handling is more likely to be load-bearing than a register allocation choice.

### What is not known

Whether it is *correct*. `non_argument_as_local` is a promise that no non-argument register is
relied on across a call boundary in a way the static analysis cannot see. `non_volatile_as_local` -
arguably the riskier of the two - has been on all along, which is mild evidence the analysis is
trustworthy, but that is an argument, not a test. **This needs a device: boot, reach a field scene,
and check the game still behaves.**

And whether it is *faster*. 36% fewer context accesses should translate into real time, because
those accesses are memory traffic in the hottest code in the process. But "should" is exactly the
word that has already been wrong twice here.

## 4. What to do when a device is next available

In order:

1. Boot with the new codegen and confirm the game still works. Correctness before speed.
2. `python tools/profile_quest.py` in a field scene. All 27,080 recompiled functions are real
   symbols in `libreblue.so`, so simpleperf names them with no instrumentation.
3. Compare the frame breakdown's `elsewhere` figure against the ~180ms recorded before.
4. Only then consider the `volatile` experiment, behind a flag, with the spin-loop hazard in mind.

The profiler exists and is committed; it has never been run, because the headset has been offline
since it was written.
