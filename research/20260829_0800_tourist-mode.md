# Research: tourist mode, and a hook that looked right and never ran

Date: 2026-08-29 08:00
Topic: fork goal 4 - infinite HP for sightseeing in VR - built and verified without a headset.

Standing in a Blue Dragon field and looking at it is the reason for this port. Being killed by a
wandering monster while doing so is not part of that, so `bd_tourist_mode` keeps the party topped up.

## The implementation is three lines

`PlayableCharacter::SetHP` already mirrors the engine's own clamp, so asking for 999999 lands on the
member's real maximum and nothing has to be discovered about where max HP is stored. Per frame, for
each party member, ask for far too much.

## The seam was the whole problem

`bdPlayerFieldMovementUpdate` (0x82207858) is *the* obvious choice - the field's per-frame movement
step, named in `config/functions.toml`, runs while walking and not in menus or cutscenes. It was
hooked, the build was clean, the game ran, and nothing crashed.

**The hook never fired once.** With the player standing still there is no movement to update, so a
midasm hook on it is dead code in exactly the scene it was written for. A clean build and a running
game said nothing about whether the feature existed.

The fix was to call it from a hook already *proven* to run every frame - the camera projection hook
added for stereo, which fires once per view whether or not anybody is walking. Semantically it is
the wrong place and it is documented as such; empirically it is the difference between a feature and
a plausible one.

## Verified, on the desktop loop

```
[tourist] party 0/1: HP 40 -> 40 (setHP=true setMP=true)
```

`setHP` returning true is the write succeeding. HP staying at 40 is the clamp working: a level-1 Shu
has 40 maximum HP, so a request for 999999 correctly lands there. Both facts were needed - the value
alone is what a silently failing write looks like, and the return alone does not prove the clamp.

## The pattern, again

This is the fifth time in this port that a correct-looking change produced no effect and only an
explicit check found it: MSAA measured at the title screen, `bd_debug_max_draws` moving two
variables, stereo doubling the post chain, a matrix read from draws that never write it, and now a
hook on a function that never runs.

**A clean build and a running game are not evidence that a hook fires.** Log the entry, once, and
look.

## Left undone

Encounter suppression. `bdPlayerFieldCheckEncounter` (0x82209678) is named and is the obvious gate,
but suppressing it needs either a control-flow redirect to the function's return - whose address is
not yet known - or a replacement that can still call the original. Infinite HP already makes
sightseeing safe, so this is a comfort improvement rather than a blocker.
