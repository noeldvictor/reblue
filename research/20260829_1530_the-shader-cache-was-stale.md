# The per-eye skew was in no shader at all, and the second layer is still empty

2026-08-29, continuing from `20260829_1500_looking-at-the-frame.md`. That note ended with "12
multiview pipelines against 201 mono" as the reason stereo carries no depth. **That reason was
wrong**, and chasing it turned up a real bug underneath.

## The pipeline ratio was a red herring

Pipeline counts are cumulative unique creations, not draws. Adding the layer count to the existing
per-surface census (`NoteDrawTarget` now carries `layers`, printed as `WxHxNL`) settles it directly:

```
target 0001BBCACAD0  344x180x2L:   67 draws/frame
target 0001BBCB0790  344x180x2L:   67 draws/frame
target 0001BBCB25D0  344x180x2L:   66 draws/frame
target 0001BBCB1FD0 1376x720x2L:    2 draws/frame
target 0001BBCA6D50  344x193x2L:   33 draws/frame
```

**Every scene surface is two-layer and taking real draw counts.** A dozen unique multiview pipelines
serve them all comfortably. So the targets were never the problem.

## The shader cache was built by a stale recompiler

Dumping the translated HLSL (`--target reblue_shader_hlsl_dump`) and grepping for the skew:

```
vertex shaders containing eyeSign: 0 of 55
```

Zero. `g_StereoSeparation` was *defined* in every shader and read by none of them - `SV_ViewID` was
not declared either. The entire per-eye skew had never been in a single shader.

Not a `#ifdef REBLUE_RECOMP` problem: that define is set (`thirdparty/CMakeLists.txt:13`, and the
host build's own cache carries `-DREBLUE_RECOMP`). **The XenosRecomp binary was simply older than
the source.**

```
shader_recompiler.cpp                       Aug 29 12:16
out/host-xenosrecomp/.../XenosRecomp.exe     Aug 28 23:43
```

`REBLUE_XENOSRECOMP` points at `out/host-xenosrecomp/`, a separate host build tree, and nothing
rebuilds it as part of the Android build. So the recompiler change landed, was committed, and every
shader kept being generated by yesterday's binary.

**And the shader cache does not depend on the recompiler binary either.** After rebuilding
XenosRecomp, `ninja` still said *"no work to do"* for `reblue_shader_cache_gen`, and
`generated/shader_cache.cpp` kept its old timestamp. It only regenerated after deleting it by hand.

So a recompiler change needs **two** manual steps before it reaches the device:

```sh
cmake --build out/host-xenosrecomp --target XenosRecomp
rm -f out/build/android-arm64-release/generated/shader_cache.cpp
cmake --build --preset android-arm64-release --target reblue
```

After that: **55 of 55** vertex shaders carry

```hlsl
in uint iViewID : SV_ViewID,
const float eyeSign = (iViewID == 0) ? -1.0f : 1.0f;
oPos.x += eyeSign * (g_StereoSeparation * oPos.z - g_StereoConvergence * oPos.w);
```

This is a real fix and it was invisible from everything except the emitted HLSL. Every "multiview is
wired up" claim made before today was true of the C++ and false of the shaders.

## And the second layer is still black

With the skew genuinely compiled in, the captured frame's disparity did not move: +58 at the sky,
+56 at the near ground, still 2px across the whole depth range.

Capturing each layer on its own (`bd_stereo_debug_layer`, which points the flat present's SRV at one
array slice) shows why:

- **layer 0**: the scene, correct.
- **layer 1**: entirely black. Mean difference between them 125/255.

So nothing is rasterising into view 1. Everything that could explain that has been checked and is
correct:

| | |
| --- | --- |
| Scene surfaces | `arraySize = 2`, confirmed in the census as `2L` |
| Attachment view | plume's base `imageView`, `VK_IMAGE_VIEW_TYPE_2D_ARRAY`, `layerCount = 2` |
| Framebuffer render pass | `VkRenderPassMultiviewCreateInfo`, `viewMask = 3` - logged per creation |
| Pipeline render pass | `viewMask = 3` - logged on creation |
| `VkFramebufferCreateInfo::layers` | 1, which is what the spec requires under multiview |
| Device feature | queried, then chained into `vkCreateDevice`; logs `multiview feature ENABLED` |
| Device limit | **`maxMultiviewViewCount = 6`** on the Adreno 650 - added to plume for this |

That is the whole chain, and all of it is right. The next thing to try is a shader that writes an
unmistakable constant colour keyed on `SV_ViewID`, which separates "view 1 is never rasterised" from
"view 1 is rasterised and something later overwrites or fails to resolve it" - the two remaining
possibilities, and they need completely different fixes.

## Worth keeping

The capture facility earned its cost again here. Every step of this - the census layer counts, the
zero-of-55 HLSL grep, the black layer 1 - is a number or an image, and the one conclusion drawn
without one (the pipeline ratio) is the one that was wrong.
