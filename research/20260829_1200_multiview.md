# Research: Vulkan multiview stereo, end to end

Date: 2026-08-29 12:00
Topic: one draw rendering both eyes, instead of submitting every draw twice.

`bd_stereo` works but submits every scene draw a second time, which cost ~8ms of CPU a frame on a
Quest - on a frame that is now entirely CPU-bound. Multiview renders both eyes from one submission,
with each vertex shader invocation told which eye it is by `SV_ViewID`.

## The pieces, and where each lives

| piece | where | what |
| --- | --- | --- |
| view masks | forked plume | `viewMask` on the pipeline and framebuffer descs, chaining `VkRenderPassMultiviewCreateInfo` into both render pass creations with a correlation mask |
| **feature enable** | forked plume | `VkPhysicalDeviceMultiviewFeatures` queried and chained into device creation |
| per-eye geometry | forked XenosRecomp | every vertex shader takes `in uint iViewID : SV_ViewID` and ends with an off-axis skew signed by the view index |
| layered target | `surface_pool.cpp` | scene surfaces get `arraySize = 2`; the sampling view stays a plain 2D view of one layer |
| framebuffer mask | `draw_framebuffer.cpp` | `viewMask = 3` when the attachment is layered |
| pipeline mask | `pipeline_state.h`, `pipeline_cache.cpp` | `multiview` is part of the PSO key, because a multiview pipeline is built against a multiview render pass |

## The trap: core does not mean on

`VK_KHR_multiview` is **core in Vulkan 1.1**, and plume targets 1.1, so it was reasonable to assume
it was simply available. It is not: the feature still has to be queried through
`VkPhysicalDeviceMultiviewFeatures` and explicitly enabled at device creation.

Without that, **a render pass view mask is silently ignored.** No validation error, no crash, no
warning. The pass renders view 0, every other layer stays cleared, and from the outside it looks
exactly like success: the frame is correct, the draw count does not double, and every log line says
what you want it to say.

It was caught by sampling layer 1 and finding it black - `bd_stereo_debug_layer` exists for exactly
that, creating the present-time sampling view with `arrayIndex` 0 or 1.

**The general lesson, which this project keeps relearning:** "it renders and nothing crashed" is not
evidence a feature works. The thing that found this was looking at the output the feature is
supposed to produce, not the output it happens to share with the path that already worked.

## Second bug, found while checking the first

The per-eye constants were written only when `bd_stereo` was set. With multiview alone the skew was
zero, so even a correctly rendered second layer would have been identical to the first - the test
could not have distinguished a working multiview from a broken one. Both paths now drive them.

## State

**Both layers render.** Layer 1 contains the scene where it was previously black, verified by
screenshot.

**Layer 1 is dark**, because the post-process chain is still mono: it reads and writes layer 0, so
the second eye gets raw scene colour without the tone and lighting passes. That is the next piece -
either the post chain becomes multiview too, or it runs per layer.

Not yet measured on the Quest, and the CPU saving over `bd_stereo` is the entire point, so that is
the measurement that matters.
